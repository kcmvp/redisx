## 1. Background & Motivation

redisx 目前的 typed document 体系（`x.Document` [x.go#L261-L292](file:///Users/kcmvp/sandbox/redisx/x/x.go#L261-L292)）存在如下 4 个结构性缺口：

### 1.1 缺口一：Doc 注册是「懒加载 & 无全局注册表守卫」

今天的 `requireRegistered[D]`（由 `StorageKey/StorageKeyValue` 等触发）是 **lazy per-type 首次调用 panic 冲突**：两张 Doc 表共用一个 `Namespace()` 但 `KeyAttrs/TTL` 不一致时，只有在两张表**都被用到时**才会 panic —— 这会让上线几周后的生产流量触发首次 panic，失败窗口太晚，没有「启动期 eager 检测」的门控。

### 1.2 缺口二：Index 和 Doc 的关系是「隐式通过泛型参数 [D] 关联」，不是一等关系

注册 index 的唯一入口是 `server.Start(address, dbPath, indexes ...x.Index)` [srv.go#L460-L488](file:///Users/kcmvp/sandbox/redisx/server/srv.go#L460-L488)，而 index 与 D 的绑定是靠用户**记得**用 `x.Idx[D]()` 构造（内部走 `IdxFullName[D]`），没有任何 registry 层断言「这个 index 名属于哪个 ns，ns 有没有对应的 Doc schema」。

### 1.3 缺口三：原生 RESP wire 协议侧（SET/UPDATE/DEL/SEARCHINDEX）无法反向路由到 Doc 类型

用户用 `redis-cli SET user:0100 '...'` 时，今天的实现**完全不知道 `user:` 这个 ns 对应了哪张表**，所以享受不到：
- `D.TTL()` 默认 TTL 自动应用
- `D.KeyAttrs` 与 JSON 内容一致性校验（防止 `user:0100` 存的 JSON id=9999）
- 「未注册 ns 直接写入」的严格性 —— 相当于裸 KV 可以随便绕过表定义

### 1.4 缺口四：没有「动态 CREATE TABLE / CREATE INDEX」

今天的 D 类型只能在 Go 编译期定义、只能在 `Start()` 参数里 eager 注册 Index；没有对应的运行时 RESP 命令，也就没有「!cmd 引导用户建表 + 元数据持久化 + 崩溃重启自动恢复」这条链路。

## 2. Design Goals

本 FR 把 redisx 重新定位为「**embedded typed JSON document store with RESP wire protocol compatibility**」。对齐以下 4 条硬目标：

| ID | 目标 | 验证方式 |
|---|---|---|
| G1 | **Doc = Table。Namespace = Table Name。** 所有写入/删除/索引查询命令 → namespace 未注册 = 直接 ERR，不做任何数据变更。 | RESP SET/UPDATE/DEL/SEARCHINDEX 针对未注册 ns → 错误码和错误信息符合第 6 节；零行数变更。 |
| G2 | **注册双通道**：启动时 eager + 运行时 dynamic；两种通道语义完全等价（CREATE TABLE IF NOT EXISTS 幂等）。 | `server.Start(..., server.Doc[UserDoc]())` 和运行时 `db.RegisterDoc[UserDoc]()` 两次连续调用 → 都返回 success 且注册表一致。 |
| G3 | **Index 一等关系**：Index 与 Doc 解耦（不写进 `x.Document` 接口），但通过 `RegisterIndex[D](logical, jsonPath)` 绑定；支持 RESP `REGISTER INDEX` 动态建索引、`DROP INDEX` 删索引；buntdb 原生回填能力直接复用。 | 先写入 10k 行 `user:*` 数据 → `REGISTER INDEX ON user(age, age)` → SEARCHINDEX 能立刻在全量数据上返回结果，无需重启/重放。 |
| G4 | **全链路严格校验（无任何兼容模式 / 无逃生舱）**：<br/>- Client 对外只有 8 个 typed `[D]` API public，raw CRUD 全 private（P1-A）<br/>- Strict DEL 预检查全 key，任一 ns 未注册 → 整体 ERR（原子不半写）<br/>- KeyAttrs 严格匹配，storage key 后缀与 JSON KeyAttrs 值不一致 → 写入前 ERR，整体不写 | 见第 7 节「MVP DoD」。 |

**Non-Goals（MVP 不做，卡位接口即可）：**
- 不做 `REGISTERTABLE <ns> <schema JSON>` RESP 命令（仅做 Go 端 `DocFromSpec` + `!cmd` 引导的后续接口卡位）
- 不做跨 Doc 的事务 / ACID rollback
- 不做 per-Doc Hook 路由（只在 `server.Doc[D](hooks ...DocHook[D])` 的签名上卡位）
- 不做 `DROP DOC <ns>` / `DROPTABLE` RESP 命令（只在 Strict 矩阵里假设不存在，所有删表只能靠直接删 key + 后续补命令）
- **不做 `OrphanNamespaces() → []string` ctrl helper（用户 2026-08-22 决策：先不考虑）**。现有用户升级时的临时 workaround：运维用原生 `KEYS *` 全扫后，脚本里按 §11 `SplitStorageKey` 拆 storageNs → dedupe → 与 `db.RegisteredDocs()` storageNs 列表 diff，找出 orphan 手工处理。MVP 交付后如果升级体验反馈差，再下一个 patch 版本补 OrphanNamespaces。
- 不做 `REINDEX` / 索引一致性校验工具（后续版本）

## 3. Core Model (Doc ↔ Index ↔ Storage Layer)

> ⚠️ **架构前置依赖**：在实现任何 Core Model 逻辑之前，**必须先完整阅读并实现 §11「系统级全局分隔符 & 命名规范 SSoT」**。本节所有键形状示例、IdxFullName 推论、KeyAttrs 多段拼接、mem 层双层 namespace、Strict 白名单判定、ScopeGuard 拆分算法 —— 全部直接建立在 §11 的 3 条**底线分隔符约定**和 3 条**推论**之上。不先实现 §11，本节所有示例会全部失效。

### 3.1 类比锚定（保持数据库直觉一致）

| redisx 概念 | SQL 对应 | 约束（MVP 严格） |
|---|---|---|
| `x.Document` 类型 D | `CREATE TABLE` 表定义 | 1 D = 1 ns；Mem/KeyAttrs/TTL 是表级属性 |
| Namespace（D.Namespace()） | TABLE_NAME | 全局唯一；在 registry 和 storage 层用同一个「§11 定义的 storage namespace 拆分算法」（见 [architecture.md SSoT](file:///Users/kcmvp/sandbox/redisx/docs/architecture.md)） |
| KeyAttrs | PRIMARY KEY (composite, multi-segment) | 多段用 **`_` 连接**（§11 约定 3，`KeyAttrsJoin`），如 KeyAttrs=[tenant,id] → storage key = `<ns>:<tenant>_<id>` |
| DocIndex（logical index on D） | `CREATE INDEX` on a table | 1 D ↔ N logical indexes；**full index name = `[_m_:]<ns>_<logical>`**（§11 推论 1，IdxFullName 新格式） |
| RegisterDoc[D]() | `CREATE TABLE IF NOT EXISTS` | 幂等；schema 不兼容 → 明确报错并列出差异 |
| RegisterIndex[D](name, path) / `REGISTER INDEX` | `CREATE INDEX` | 动态可加；buntdb 即时回填已有数据 |
| Strict Mode（默认，无开关） | `sql_mode=STRICT_TRANS_TABLES` | 未注册 ns 的写/删/索引查询 → ERR |

### 3.2 「Index 挂 Doc」模型：A1 外部关系一等化

**关键设计决策：`x.Document` 接口**维持今天的 [x.go#L261-L292](file:///Users/kcmvp/sandbox/redisx/x/x.go#L261-L292) 5 个方法**完全不变**，不新增 `Indexes()` 方法。Index 与 Doc 的关系通过**外部 registry** 一等关联，不是 Doc struct 的字段/方法：

```
                    ┌───────────────────────────────────────────────────────────────┐
                    │        Doc Registry (global — memory only, non-SSoT)          │
                    │                                                                 │
                    │  ns -> RegistryDocEntry{                                       │
                    │    PersistentDocSpec (ssot snapshot, NO indexes field)         │
                    │    + IndexesRuntimeCache: []IndexSpec  ← 非持久化，非 SSoT     │
                    │                              每次 DescribeDoc 强制重算，不用 trust │
                    │    CreatedAt, TypeName                                         │
                    │  }                                                              │
                    └────▲─────────────────────────────────────▲─────────────────────┘
                         │                                     │
         RegisterDoc[D]() │            RegisterIndex[D](name,path)│
          (Go typed API)  │         (Go typed / RESP cmd)        │
                         │                                     │
     ┌──────────────┐    │     ┌──────────────────────────────┐
     │  x.Document  │    │     │  x.Index (existing)           │
     │  interface   │    │     │  name/keyPattern/path         │
     │  (unchanged) │    │     │  (underlying impl, unchanged) │
     └──────────────┘    │     └──────────────────────────────┘
                         │
              ┌──────────┴─────────────────────────────────────────────────┐
              │  storage (buntdb two-layer — 真正 SSoT, 永远两套分开)          │
              │  ① 用户数据行:                                               │
              │      <ns>:<pk>                        → disk JSON rows      │
              │      _m_:<ns>:<pk>                    → mem JSON rows       │
              │  ② 元数据 (两套独立, 绝对不合并):                                │
              │      _doc_:<storageNs>                → PersistentDocSpec   │
              │                                              (NO indexes)   │
              │      _idx_:<[_m_:]<ns>_<logical>>     → IndexSpec           │
              │                                              (独立 KV)     │
              └─────────────────────────────────────────────────────────────┘
```

> **三套 struct 严格分离（A1 模型的核心保障，用户 2026-08-22 决策：元数据分开）**：
>
> | Go 结构体 | 出现位置 | 是否持久化（_doc_:* / _idx_:*） | 是否允许出现 `indexes` 字段 | SSoT 来源 |
> |---|---|---|---|---|
> | **`x.PersistentDocSpec`** | `_doc_:<ns>` 磁盘 JSON / `db.RegisterDocFromSpec(spec)` 入参 / RESP `REGISTERTABLE <ns> <json>` 入参 / `!CREATEDOC` 输出 | ✅ 是（= 磁盘格式 byte-for-byte）| ❌ **绝对禁止**（任何包含 `indexes` 字段的 spec → `ERR PersistentDocSpec must not contain indexes; use REGISTER INDEX separately`）| 用户决策：元数据分开，Index 可以后定义 |
> | **`x.IndexSpec`** | `_idx_:<full>` 磁盘 JSON / `db.RegisterIndexFromSpec(spec)` 入参 / RESP `REGISTER INDEX <full> <json>` 入参 / `!REGISTER INDEX` 输出 | ✅ 是 | *(不适用，独立 struct)* | Index 自身独立存在，通过 `full = [_m_:]<ns>_<logical>` 中的 `<ns>` 段天然归属 Doc（§11 推论 1）|
> | **`x.DescribeDocResult`** | `db.DescribeDoc(ns)` 返回给业务层 / RESP `DESCRIBEDOC <ns>` 返回值 | ❌ 不持久化（运行时拼装）| ✅ **允许**（聚合返回给用户看）| 运行时先读 `_doc_:<storageNs>` = PersistentDocSpec → 再 glob `_idx_:<ns>_*` 列齐所有 IndexSpec → 两者拼成 DescribeDocResult。**永远不把 DescribeDocResult 序列化回磁盘**（否则就会出现 schema 冲突）。|
> | **`internal.registryDocEntry`** (internal 包私有，不 export) | 内存 registry map ns→entry 的 value | ❌ 纯内存 | 可带 `indexesRuntimeCache`，但每次 DescribeDoc 必须**忽略 cache** 重新 glob 重算（cache 仅作 debug 用，非 SSoT）| - |

A1 模型为什么是 MVP 正确的选择（vs A2 Indexes() 写进 D 接口）：

1. **Doc 是「宽泛的表形状」** — 只定义关键属性（Namespace/KeyAttrs/Mem/TTL/RawJSON），符合你最初的直觉；Index 是「可选加速结构」，与 shape 解耦。
2. **动态 CREATE INDEX 在类型层面天然可行** — Index 不是 D 的编译期属性，运行时加不需要改 Go 类型定义。
3. **零破坏** — 任何已有的 `type UserDoc string` 实现代码不需要改一行；index 迁移是纯加功能。

### 3.3 「Namespace 约定」与 ScopeGuard 关系

Namespace 的**拆分与拼接规则**（含 mem 层两层 namespace + Strict 白名单 + scope 防越界）**全部以 §11 System-Level SSoT 为唯一 SSoT**，architecture.md 只引用不重述。对齐要点：

- 全局 storage key 形状（disk / mem / internal 统一格式）：**`<storageNs>:<pk-suffix>`**，其中 `<storageNs>` =
  - Disk 用户 Doc = `<namespace>`（纯 ns 名，如 `user`、`trade`）
  - Memory 用户 Doc = **`_m_:<namespace>`**（§11 约定 2，**中间有冒号**，是两层 namespace 节点：`_m_` → `user` → pk）
  - Internal 元数据 Doc / Index = **`_doc_` / `_idx_`**（本身就是完整 storageNs，再用 `:` 接 suffix → 得到 `_doc_:user` / `_idx_:user_age`）
- `<pk-suffix>` 拼接：单段 KeyAttrs → 直接值；**多段 KeyAttrs=[tenant,id] → tenant 与 id 用 `_` 连接**（§11 约定 3，KeyAttrsJoin）→ 整体 storage key = `<storageNs>:<tenant>_<id>`；**pk-suffix 内部永远不出现 `:`，只出现 `_` 分隔。**
- Strict 检查、KeyAttrs 一致性校验、REGISTRY 反向 lookup、ScopeGuard（[server/key_range.go#L25-L53](file:///Users/kcmvp/sandbox/redisx/server/key_range.go#L25-L53)）全部复用 §11 推论 3 导出的同一个共享 helper（未来在 `internal/shared.go` 新增，不得散落硬编码），确保不漂移。

## 4. Two Registration Channels (Eager + Dynamic)

### 4.1 Channel 1 — Start / Open: Eager Bulk Registration（启动时）

将今天的 `server.Start(address string, dbPath string, indexes ...x.Index)` [srv.go#L460](file:///Users/kcmvp/sandbox/redisx/server/srv.go#L460) 升级为 **functional options 风格**（向后可迁移）：

```go
func Start(address, dbPath string, opts ...StartOption) *DB

// Start options:
func Doc[D x.Document](hooks ...DocHook[D]) StartOption   // ← CREATE TABLE eager
func DocFromSpec(spec x.PersistentDocSpec) StartOption       // ← non-generic CREATE TABLE (for tooling)
func RawIndex(def x.Index) StartOption                     // ← 仍然保留作为 helper；Strict 下如果与 D 的 registry 冲突则整体报错
func IndexOn[D x.Document](logicalName string, jsonPath string) StartOption // ← CREATE INDEX eager
```

**调用例子（MVP 最终用户体验）：**

```go
server.Start(":6379", "/data/redisx.db",
    // Eager 注册 3 张表（等价三张 CREATE TABLE IF NOT EXISTS）
    server.Doc[UserDoc](),
    server.Doc[OrderDoc](),
    server.Doc[TradeDoc](),

    // Eager 挂索引（等价 CREATE INDEX）；也可以完全不写这里，运行时 REGISTER INDEX 动态建
    server.IndexOn[UserDoc]("age", "age"),
    server.IndexOn[UserDoc]("email", "contact.email"),

    // RawIndex 兼容：如果 RawIndex 挂的 ns 已注册 D 且 D.Indexes 列表（运行时）
    // 没有对应条目 → 启动期整体 ERR（fail closed，不留灰区）
    server.RawIndex(x.RawIndex("external_log_lvl", "ext:*", "level")),
)
```

**启动期关键执行顺序（在 srvOnce.Do 内，srv.go L464-530）：**

```
1. openDB(dbPath)                              — 不变
2. loadAuthKeyLimits(db)                        — 不变
3. loadSchemaRegistryFromDB(db)                 — [新增] 扫 `_doc_:*` + `_idx_:*` 两个 glob key pattern，
                                                     自动从磁盘元数据重建 Doc/Index 注册
4. process opts:
     a. Doc[D]() / DocFromSpec()                → 调 RegisterDoc / RegisterDocFromSpec（与 channel 2 同一实现，冲突即 ERR）
     b. IndexOn[D]()                            → 调 RegisterIndex[D]（同一实现）
     c. RawIndex(...)                           → 调 db.registerIndexes；冲突即 ERR
5. srv.ListenServe(addr)                        — 不变
```

**关键性质：** step 3 与 step 4 任一失败 → `db.Close()` + slog.Error + `exitFn(1)`（启动失败不服务，fail closed 对齐 Strict 精神）。

### 4.2 Channel 2 — Runtime Dynamic Registration（运行时）

在 `*DB` 上挂 4 个一等方法：

```go
// ─── CREATE TABLE 家族 ───
func (db *DB) RegisterDoc[D x.Document]() error
func (db *DB) RegisterDocFromSpec(spec x.PersistentDocSpec) error

// ─── CREATE/DROP INDEX 家族 ───
func (db *DB) RegisterIndex[D x.Document](logicalName string, jsonPath string) error
func (db *DB) DropIndex[D x.Document](logicalName string) error
```

以及 ctrl 可观测性：

```go
func (db *DB) RegisteredDocs() []x.PersistentDocSpec                    // SHOW TABLES NAMES+SCHEMA（仅持久化 schema，不含 indexes）
func (db *DB) DescribeDoc(namespace string) (x.DescribeDocResult, bool)  // DESCRIBE <ns>（聚合快照：PersistentDocSpec + 此时刻所有 indexes）
func (db *DB) ClassifyKey(storageKey string) (ns string, registered bool, spec x.PersistentDocSpec) // debug helper（只需要 schema 不需要 indexes）
func (db *DB) RegisteredIndexes(ofNamespace string) []x.IndexSpec        // SHOW INDEX FROM <ns>（等价单独 glob _idx_:ns_*）
```

**4.2.1 RegisterDoc[D] 严格语义：**

```
RegisterDoc[D]() 执行步骤
  ① lock(registryMutex) 持全局写锁
  ② 计算 DocSpecFor[D]()：
       storageNs = Mem() ? "_m_" + Namespace() : Namespace()
       keyattrs, ttl, typeName 从 D 反射/调用得到
       indexes = 当前 D 已通过 RegisterIndex 绑定的 logical indexes
  ③ documentRegistry CAS ns → spec:
       - 未存在 → 写入；写 `_doc_<ns>` = spec JSON 到 buntdb disk；返回 nil
       - 已存在 → 全等对比（keyattrs/ttl/mem/typeName）
            * 全等 → 幂等成功（CREATE TABLE IF NOT EXISTS）
            * 任一不同 → 返回结构化 ERR（列出所有差异字段：期望 A，实际 B）
  ④ unlock
```

**4.2.2 RegisterIndex[D] 严格语义：**

```
RegisterIndex[D](name, path)
  ① lock(registryMutex)
  ② 确认 ns = storageNamespace[D] 已在 documentRegistry 中注册
     → 未注册 → ERR："cannot register index 'age' on table 'user': table not registered (call RegisterDoc[UserDoc]() first)"
     → 注册好了 → 继续
  ③ 拼 full index name = IdxFullName[D](name)
     拼 keyPattern   = storageNs + ":*"
     拼 buntdb path  = strings.ReplaceAll(path, ".", "_")
  ④ buntdb.Tx.CreateIndex(fullName, keyPattern, buntdb.IndexJSON(path))
     → 已存在同名 fullName 且 path 相同 → 幂等 OK
     → 已存在同名 fullName 但 path 不同 → ERR（buntdb 报错向上冒泡）
  ⑤ registry 里 D.DocSpec.Indexes append((name, path, full))
     写 `_idx_<full>` = spec JSON 到 disk
  ⑥ unlock
```

**重要实现说明（buntdb 回填利用）：** step ④ 的 `CreateIndex` 在 buntdb 里是 O(n log n) 的同步建索引操作 —— **已有的全量 `<ns>:*` 行立刻进入 BTree**，无需 redisx 自己重扫数据。MVP 直接依赖这个原生能力，不自己写回填 loop。

### 4.3 RESP wire 的 REGISTER / DROP 命令（MVP 对齐 Index）+ 传统 Redis SET/GET 语义糖扩展

MVP 就落地 2 条 RESP 扩展命令（对应 Channel 2 的 Index 家族）。注意：**REGISTER/DROP 官方命令词是 UI 糖（人类 Shell 输入读），RESP 线上实际命令字统一为 ADM 前缀 regidx / delidx**（见 Ctrl Shell Child FR §7）。原因：① 和 Doc 管理命令（regdoc 等）风格统一 ② Server 端 Gate1 App-port 构建显式白名单：遍历 proto.Registry Role==CtrlOnly 的全部命令字（regdoc/lsdoc/desdoc/lsidx/regidx/delidx）— Fail-Closed，不会漏判以后加的 Ctrl 命令。③ 未来业务命令如果要加 CREATE 动词不会和管理命令命名空间冲突。

**人类 UI 糖（Shell / 文档阅读友好）：**
```
REGISTER INDEX ON <namespace> (<logical_name>, <json_path>)
DROP INDEX     <namespace>.<logical_name>
```

**例子（redis-cli 发送 ADM 前缀实命令字）：**
```redis-cli
regidx user (age, age)
regidx user (email, contact.email)
delidx user email
```

> Child FR §7 有 Sugar-Command → RESP-args 的完整映射表；Shell 端实现 sugar-to-wire 转换，Server 端只认 ADM 前缀，不认 REGISTER/DROP 命令字。

> Doc 家族的 RESP `REGISTERTABLE <ns> <schema JSON>` MVP 先不做，但在 cmd.go 解析器中**预留关键字**，收到后返回 `ERR REGISTERTABLE is not implemented yet; use db.RegisterDocFromSpec(spec) or !CREATEDOC`。未来 `!cmd` 体系落地后再打通。

**4.3.2 MVP 命令最终形状总表（22 条，用户 2026-08-22 拍板 Q1/Q2/Q3 + C2/C4，Fail-Closed）**

> **MVP 硬约束（Fail-Closed 总原则，handleCommand 入口处统一预检，不进入具体 handler）：**
> 1. **Q2（结论 3 5 条核心命令 = SET/SETEX/SETNX/GET/DEL）：第 1 参数只能是 storageNs（纯 namespace，不能含 `:`；mem 层 storageNs 整体为 `_m_:<ns>`，允许 ns 参数整体含一个 `_m_:` 前缀，除此外不允许其他形式含 `:`）。旧形式「第 1 参数 = full storageKey `<ns>:<pk>`」直接 ERR，不做任何回退兼容。**
> 2. **Q1（SEARCHKEY）：保留命令字不改，但参数形状强制为两参数 `<storageNs> <pk-range_json>`，旧单参数「完整 KeyRange JSON」形式直接 ERR。**
> 3. **Q3（KEYS）：仅接受单参数 `<storageNs>`（不接受任何 glob pattern，不论 `user:*` 还是 `abc*`，全部直接 ERR）— 避免「通配符匹配时还要区分 mem/disk 层」的歧义复杂度。**
> 4. **C2（SEARCHINDEX）：仅参数 `<index_full_name> <filter_json>`（表面维持今日两参数形状，内部新增 2 道 pre-check：① index name 必须能按 §11 规则反向解析出 storageNs ② 解析出的 ns 必须已注册 + `_idx_:<full>` 元数据必须存在）**
> 5. **C4（UPDATE）：维持今日 `UPDATE <full_storageKey> <mutation_json>` 两参数形状不变（等价传统数据库 UPDATE ... WHERE key = ...），仅内部加 2 道 Strict Gate（① ns 注册校验 ② mutation 后 KeyAttrs 一致性校验）。**

**4.3.3 Internal shared helpers（所有命令的实现依赖，§11 推论 3 再次强化）**：
上文 4 类 22 条命令的参数解析、storageNs 定位、pk-suffix 合法性校验、KeyAttrs 反向重匹配 — **全部依赖 §11 推论 3 列出的 4 个共享 Go helper**（放在 `internal/shared.go` 或 `x/contract/shared.go`，不允许散落写在每个 handler 里）：

- `IsInternalStorageNs(storageNs) → bool`（前缀白名单 `_auth_`/`_doc_`/`_idx_`/`_m_`）
- `StripMemPrefix(storageNs) → (underlyingNs string, mem bool)`（判断是否 mem 层并剥 `_m_:`）
- `ExtractPKSuffixes(pkSuffix string, segCount int) → ([]string, bool)`（按 `_` 拆 pk 多段，segCount 与 KeyAttrs len 对齐）
- **新增 `ParseIndexFullName(raw string) → (storageNs string, logical string, mem bool, ok bool)`**（§11 IdxFullName 反向解析器：先检测 `_m_:` 前缀，然后在剩余部分取**第一个 `_` 之前 = storageNs，之后 = logical**；专门供 SEARCHINDEX / REGISTER INDEX / DROP INDEX 三个命令使用，不许散落写字符串 split 代码）

Typed client API（`DBX[D].Set(doc)` / `SearchIndex[D]` / 等）**完全复用 server 侧同一套 helper 的反向实现**（StorageKeyValue[D] 现在的 `:` + `_` 拼接）：保证 wire command（糖放在 server 算 pk）和 typed client（放在 client 算 pk）**两条路径 byte-for-byte 一致，不会各算各 bug**。

### 4.4 `!cmd` 引导入口的元数据规范卡位

你提到的「会有一个 !cmd 引导用户创建 Doc」，MVP 只**卡位元数据的磁盘格式**，不实现 !cmd shell 本身：

```
_doc_:user      = { "ns":"user", "mem":false,
                    "keyattrs":["id"],
                    "ttl_ns":604800000000000,
                    "type_name":"main.UserDoc",
                    "created_at":"2026-08-22T12:00:00Z" }

_idx_:user_age = { "ns":"user",
                   "logical":"age",
                   "path":"age",
                   "full":"user_age",
                   "created_at":"..." }
```

> **关键命名约定（解决 Index 归属定位 + 冲突零可能）（与 §11 SSoT 对齐）：**
> 1. **Doc 元数据键** = **`_doc_:<namespace>`**（§11 约定 1 + `_doc_` 是 internal storageNs，再接 `:` suffix）。示例：`_doc_:user`, `_doc_:order`, `_doc_:_m_:hot`（hot 在 mem 层，mem 模式下 storageNs = `_m_:hot`，所以整体 = `_doc_:_m_:hot` —— 注意 **仍然遵循「`<storageNs>` + `:` + suffix」的全局形状**，只是 storageNs 本身是 mem 层的 `_m_:hot`，所以会出现两个 `:`。）
> 2. **Index 元数据键** = **`_idx_:<full_index_name>`**。而 `<full_index_name>` = **`[_m_:]<namespace>_<logical>`**（§11 推论 1，byte-by-byte 与 IdxFullName[D] 一致）。示例：
>    - `_idx_:user_age`（namespace=user，logical=age，full=user_age）→ 归属定位只需取 `<full_index_name>` 的 `<ns>` 段；**不再需要解析 `_idx_` 后最后一个 `_` 前缀拆分，命名约定已经把归属编码进 full name。**
>    - `_idx_:_m_:hot_price`（namespace=hot, mem=true，logical=price，full=`_m_:hot_price`）
> 3. 因为 Index full_name 天然带 `<namespace>_` 前缀 → **零可能与其他 doc 的 index 键冲突**，不需要任何额外唯一约束守卫；同时「DescribeDoc(user) 找 user 的所有 index」不用扫全库 `_idx_:*`，直接用 buntdb AscendKeys 匹配 `_idx_:user_*` 这个 key pattern 就能列齐 — 完全等价于方案 1 的 join，但性能和扫描范围都受控。
> 4. Doc spec JSON 内**不冗余存 `indexes` 字段**。DescribeDoc(user) 的 `Indexes: []` 返回值由 `_idx_:user_*` 扫描结果动态拼装。

- `_doc_` / `_idx_` 两个 internal storageNs（所有 Strict 检查对「以 `_` 开头的 storageNs」**或**「key 以 `_auth_:` 前缀开头」全部跳过，见第 5.3 节）
- 崩溃重启后 step 3 的 `loadSchemaRegistryFromDB()` 扫 `KEYS _doc_:*` + `KEYS _idx_:*` 两个 glob → 100% 恢复 registry，不需要用户重新执行 `Doc[D]()` 或 `REGISTER INDEX`。

> **`!REGISTER INDEX` shell UX 流程卡位（用户 2026-08-22 决策）**：
> Index 与 Doc 的**唯一绑定关系 = doc namespace**（不在 Doc struct/接口里存任何 index 列表）；因此管理程序/`!cmd` shell 在引导用户「新建 Index」时，**必须严格按以下 4 步顺序走（不可换顺序，不可跳过）**：
> 1. **第 1 步（强制首先选 Doc）**：shell 列出 `db.RegisteredDocs()` 所有已注册的 Doc（ns + type_name + mem? + keyattrs + ttl），要求用户**必须先选定一个目标 Doc（namespace）**。不允许先填 Index 属性再回头选 Doc（避免「先写 index name 再绑定 ns」导致的冲突可能性）。
> 2. **第 2 步（填 logical index name）**：用户输入 `logical`（在该 Doc ns 下唯一，不要求全局唯一）→ shell 立即根据 §11 推论 1 自动拼出 `full = [_m_:]<ns>_<logical>` 并展示给用户确认，**如果 full 已在 `_idx_:*` 中存在则立即报错，不让用户进入下一页**。
> 3. **第 3 步（填 Index JSON path + KeyPattern）**：用户填 `path`（JSON path，自动 normalize `.` → `_`），默认 KeyPattern = `*`（全表索引）；用户可改为 `user:*` / `_m_:hot:*` 等 Doc-scoped pattern，但 shell 必须校验 KeyPattern 必须以 `<storageNs>:` 开头（第 1 步选的 Doc 的 storageNs），禁止跨 Doc。
> 4. **第 4 步（执行 + 回填 + 落盘）**：用户点确认 → 同步调用 `db.RegisterIndex[D]()` / `REGISTER INDEX` → buntdb 同步回填已有 `<ns>:*` 行 → 落 `_idx_:<full>` meta JSON → 返回成功或失败（回填冲突：index 数据类型不一致，buntdb 错误向上冒泡）。
>
> 这条 UX 规则**同时适用于 RESP REGISTER INDEX 命令的参数解析顺序**：`REGISTER INDEX` 的第 1 个参数必须是 Doc ns（或 `Doc type_name`），第 2 个才是 logical name，第 3 个是 path —— 不允许省略第 1 个参数（因为 ns 是 SSoT）。

> **`!CREATEDOC / !SETDOCS` shell 的糖语义（自动 pk 生成，不用手拼 storage key）**：
> 既然 §4.3.2 已经把「糖 SET namespace + 单/多 JSON」定义为 server 级 Wire Command，那么 `!cmd` shell 在引导用户「写入真实数据」的步骤里，同样完全对齐：
> 1. **`!CREATEDOC` 第 2 页（填内容）**：用户选择了 Doc namespace=user 之后 → shell 的大文本框默认只填 `[{...}, {...}]` 或单 object，不需要用户写 `user:0100` 这种 storage key。shell 提交时直接调用糖 SET：`SET user <用户粘贴的 JSON>`（server 侧按 KeyAttrs 自动 pk 拼 storage key）。
> 2. **`!SETDOCS <ns>`（如果将来做批处理）** = 等价于 `SET <ns> <JSON array>`（糖 SET 多文档）。同样不需要填 storage key。
> 这条规则让「管理程序写 Index 先选 Doc、写 Doc 数据只贴文档内容」的两条链路体验完全一致（都不需要人工知道 pk 拼法/冒号/下划线），而底层 server 侧的 KeyAttrs pk 派生算法 + storageKey 拼接（`SplitStorageKey` last-colon + `ExtractPKSuffixes` §4.3.3 共享 helper）100% 复用，不会出现 !cmd shell 和 RESP wire 两条不兼容路径。
>
> Q2 单通路严格模式下 MVP **完全不提供人工直接拼 full storageKey 的逃生舱**；任何想直接写 `SET user:acme_0100 …` 形式（第 1 参数含 `:`）都会在 handleCommand 参数级 Gate 直接 ERR（精确文案见 §7.4.1）。storage key 拼法 **100% 由 server 侧 KeyAttrs 派生算法作为 SSoT**，杜绝人工拼法引入的 KeyAttrs 字段不一致 silent bug（人工写 `tenant=acme,id=0100` 却拼出 `user:acme:0100` 而不是 §11 要求的 `user:acme_0100` 这种分隔符级别错误，由 server 单点生成彻底消除）。

## 5. Strict Mode: Command Matrix（MVP 全覆盖，无兼容模式）

Strict Mode 是**默认唯一模式**，不提供开关。所有命令的严格度矩阵：

### 5.1 严格校验类（未注册 ns = 整体 ERR，零数据变更）

> **关键前置（用户 2026-08-22 Q2 最终拍板）：MVP **取消双通路**，单通路严格模式，Fail-Closed at handleCommand 入口层。**
> - **Q2：通路 A（旧显式 pk `SET user:0100 …`）永久移除**。所有旧的「第 1 参数 = full storageKey 含 `:`」形式（SET/SETEX/SETNX/GET/DEL）在 MVP 下**直接精确 ERR，不做任何回退兼容**。
> - **Q2：新的单通路严格格式（5 条核心命令）** = 第 1 参数永远 = `storageNs`（纯 namespace，mem 层 `_m_:hot` 作为一个**整体 ns 参数**允许含 `_m_:` 前缀；除此之外不允许其他形式含 `:`）；第 2 参数 = 完整 JSON（单对象/数组批量）或 pk-suffix。
> - **Q1（SEARCHKEY）：保留命令字不改，但参数形状强制为两参数 `<storageNs> <pk-range_json>`；旧单参数「完整 KeyRange JSON」形式直接 ERR**。
> - **Q3（KEYS）：仅接受单参数 `<storageNs>`（不接受任何 glob pattern，`user:*` / `abc*` 全部直接 ERR）**— 避免通配符匹配时还要区分 mem/disk 层的歧义复杂度。
> - **C2（SEARCHINDEX）/ C4（UPDATE）：** 两参数表面形状维持今日字节级不变，但内部新增 Strict pre-check（ns 注册 + KeyAttrs 一致性），具体校验点与 §4.3.2 表格字节级一致。
> - **统一 Fail-Closed 执行顺序（handleCommand 入口预检，不进具体 handler）：**
>   ```
>   handleCommand(conn, cmd, db, ps)
>     L368  db nil check            (现状)
>     L375  NOAUTH check            (现状, AUTH/HELLO/CLIENT 放行)
>     L385  [NEW MVP LAYER: 统一参数级预检]
>           ① 按命令字分类 → 结论3 / 结论2 / 其他
>           ② 按 §4.3.2 的 Q1/Q2/Q3/C2/C4 规则分别跑参数级校验
>           ③ 任何失败 → conn.WriteError(精确格式ERR文案) + return（不进入业务 handler，零数据变更）
>     L386  commandRegistry 查表进入具体 handler
>   ```
> - **Registry SSoT 不可绕过原则：** 即使 buntdb 物理 key/index 存在，只要 registry 没有对应 ns / `_idx_:<full>` 元数据 → 命令一律 ERR，不允许 silent fallback。
> - **Storage 层 SSoT 原则（与 Q2 完全兼容，无破坏）：** server 侧按 KeyAttrs 推导 pk 拼出的 **buntdb key 形状 = `<storageNs>:<pk-suffix>`（单文档单 key）**，与 §11 定义字节级一致，因此 buntdb 原生 CreateIndex 回填 / TTL per-key / AscendRange 能力 100% 复用，不会破坏 M1~M7 任何一条已锁定设计。

### 5.2 KeyAttrs 一致性校验（MVP 严格，无开关，无松动）

在 SET/UPDATE 写入前执行：

```
Inputs: storageKey (string), rawJSON (string), DocSpec (from registry)
Output: OK or ERR (整体 abort, 不写)

For (i, keyAttr) in DocSpec.KeyAttrs:
   1. expected = extract i-th pk-segment from storageKey:
        storageKey = "order:acme:0100", keyattrs = ["tenant","id"]
        → segment 1 (tenant) = "acme", segment 2 (id) = "0100"
   2. actual   = gjson.Get(rawJSON, keyAttr).String()
        → if !ok (missing field) → ERR: "missing JSON field 'tenant'"
   3. expected == actual → continue
        → else ERR: "KeyAttrs mismatch for table 'order': segment #1 (tenant) expected 'acme' from storage key, got 'evil' from JSON"

Special case: DocSpec.KeyAttrs == [] (empty) → 直接跳过这道门（允许用户定义「无 KeyAttrs 校验的宽松 Doc」，比如纯 key/value blob）
```

**UPDATE 命令的特殊处理：** mutation 可能改 KeyAttrs 字段本身（例如 `SET id = 9999`）。KeyAttrs 校验**在 mutation 之后**对「新值」执行 — 防止把某行改成 `storageKey=user:0100` 但 JSON id=9999 的脏状态。校验失败 → 整个 UPDATE 0 行变更，回滚。

### 5.3 不做 Strict 校验的例外（白名单 3 类）

1. **所有「storageNs 以 `_` 开头」或「key 直接以 internal 前缀 + `:` 开头」的 metadata 命名空间**：
   - `_auth_:*`（账号配置，已经是「前缀 + `:`」形式 → storageNs = `_auth_` 以 `_` 开头 → 白名单 ✅）
   - `_doc_:*`（Doc 元数据）→ storageNs = `_doc_` → 白名单 ✅
   - `_idx_:*`（Index 元数据）→ storageNs = `_idx_` → 白名单 ✅
   - `_m_:`（mem 层 user 行**不**在这里白名单：`_m_:user:0100` 的 storageNs = `_m_:user`；白名单只给「真正的 internal metadata 前缀」如 `_doc_`/`_idx_`/`_auth_`）。mem 层 user 行仍然必须有对应 Doc 在 registry 内。
   - 白名单判定 = **SplitStorageKey(key) → storageNs.HasPrefix("_")**（§11 推论 3 的共享 helper 统一出口，不得散落硬编码 `strings.HasPrefix(key, "_")`）
2. **运维读命令**：`GET k`（空值返回 nil，不报错 / `KEYS pattern`（全可见，包括未注册 ns 的「幽灵数据」 —— 运维命令保留全量可见性作诊断）
3. **No-Doc 基础设施**：`PING/AUTH/SUBSCRIBE/PUBLISH`（PubSub/连接/鉴权 全与 Doc 无关）

### 5.4 TTL 自动路由

无论 Strict 模式下（MVP 只有 Strict）：

```
If SET command has EX/PX explicitly in args → use user's TTL (explicit wins, minimal surprise)
Else (no TTL in SET)
   → LookupDocByKey(key) in registry
     → found: use DocSpec.TTL as buntdb TTL
     → not found: would already fail in the "table does not exist" gate anyway (strict mode)
```

**Client 侧冗余：** typed `Set[D](d)` 在发送前也做一次 `ttl = d.TTL()` 作为本地前置。Server 侧仍然以自己第 2 步 gate 计算出的 TTL 为最终值 —— 不信任客户端输入（安全边界在 server）。

### 7.4 Strict Command Matrix (Colon-Routing SSoT)

**Trust-User Principle (user ruling 2026-08-25):** "For every Redis-native command, if the key/pattern arg contains `:`, execute it with pure Redis semantics — zero registry gates, zero schema validation, zero implicit key derivation, caller owns correctness 100%. Doc-path gates only apply to args that have no `:` at all."

**Internal-Namespace Write Guard Exception (user ruling 2026-08-25):** The Trust-User principle does NOT apply to mutation of the three dedicated ctrl namespaces `_doc_`, `_idx_`, `_auth_`. Any SET/SETEX/SETNX/DEL whose resolved storageNs equals one of these three → precise ERR advising the dedicated command (REGSCH / DROPSCH / REGIDX / DROPIDX / AUTH). Read-class operations (GET / KEYS) on these three internal storageNs ARE allowed via KV-path (colon present) — e.g. `KEYS _doc_:*` remains free for ctrl introspection. `_m_:…` (mem layer) and any other underscore-prefixed forms → rejected uniformly by HasUnderscorePrefix regardless of read/write (reserved for future protocol expansion).

**Rationale:** "single structural discriminator = does arg1 contain `:`?"

- **KV-path (arg1 contains `:`)**: Redis-compatible passthrough. No registry, no schema validation, no `DocSpec.TTL` auto-apply. Caller owns correctness.
- **Doc-path (arg1 has no `:`)**: Typed-document gates apply in order (parameter → registry → business). Any gate fails → precise `ERR`; zero data mutation.

Note: Client SDK generic surface `Get[D]`, `Set[D]`, `Keys[D]`, `SearchIndex[D]`, `SearchKey[D]`, `Update[D]` always emit **Doc-path** (no `:` in arg1). The `*Raw` methods emit literal args (can drive KV-path by passing full keys with `:`).

#### 7.4.1 Parameter-Level Gates

- [x] **`SET` / `SETEX` / `SETNX` arg1 = KV → pure passthrough**. Example: `SET user:abc 'plain-bytes' EX 3600` → buntdb writes literal `user:abc` with no registry/JSON/KeyAttrs gate. Semantics are upsert-if-exists / Redis-style.
- [x] **`SET` / `SETEX` / `SETNX` arg1 = Doc (no `:`)**.
  - `SET`: argc ≥ 3. JSON = single object or non-empty array of objects. `EX/PX/NX` optional tail.
  - `SETEX`: argc = 4 exactly. Fixed `ttl_seconds` before value.
  - `SETNX`: argc = 3 exactly. Value JSON shape rules same as SET.
- [x] **`GET` arg1 = KV (contains `:`, argc = 2 total) → raw buntdb Get**. Key missing → null.
- [x] **`GET` arg1 = Doc (no `:)`. argc must be exactly 3 (`<ns> <pk-suffix>` total = 2 beyond CMD)**. Bare ns (`GET user` alone) → ERR ("namespace alone is not a query"). Suffix must not contain `:` (it's appended after BuildStorageKey).
- [x] **`DEL` arg1 = KV**. `argc == 2 → single kv delete` (user ruling 2026-08-25: KV-path DEL is **always single-key only** on this server; multi-key KV-path deletion like `DEL a:1 b:2 c:3` is intentionally not exposed and callers should issue multiple DEL commands). `argc ≥ 3 AND arg1 contains `:` → parameter ERR ("DEL kv-pattern takes one full key; issue separate DELs for multiple keys or use doc-path form"). `argc ≥ 3 AND arg1 has NO `:` → doc-path ns + ≥ 1 pk-suffix below.
- [x] **`DEL` arg1 = Doc (no `:)`. argc ≥ 3 total → ns + ≥ 1 pk-suffix**. Bare ns (`DEL user` alone) → ERR ("forbid drop-whole-collection sugar"). Every pk-suffix must NOT contain `:`.
- [x] **`KEYS`**. Single argument. Colon-routing discriminator applied to the pattern itself:
  - [x] `HasMemPrefix(pattern) || IsInternalStorageNs(pattern)` → passthrough unchanged. Covers `_doc_`, `_idx_`, `_auth_` bare storageNs and any `_m_:<ns>:*` style mem-layer globs (ctrl introspection via raw KV).
  - [x] Pattern **contains `:`** → treated as raw KV-path glob, allowed freely (wildcards + colons OK, no registry/doc gates, no auto-transform). Examples: `KEYS app:prefix*` / `KEYS user:*` / `KEYS cli:key_*` — all resolve exactly as written on the KV store.
  - [x] Pattern **has NO `:` AND contains wildcards (`*?[`)** → parameter ERR ("doc-path KEYS requires bare <storageNs> without wildcards; fragment globs like `abc*` are ambiguous because they could span namespaces").
  - [x] Pattern **has NO `:` AND no wildcards** → bare doc storageNs: (a) non-internal → **registry gate MUST be registered** (else ERR with hint to append `:*` for KV-style raw), (b) auto-scoped internally to `<ns>:*` for the actual buntdb scan.
- [x] **`SEARCHKEY`**. First arg is always a KeyRange JSON (current implementation retained). Two routing branches from `x.LayerRoutingAnchor(kr)`:
  - Anchor **contains `:`** (e.g. `"user:p1|user:p9"`) → KV-style range. No registry gate.
  - Anchor **does NOT contain `:`** → Doc-style range. Resolve storageNs from anchor; **registry gate: ns MUST be registered** (internal ns excepted).
- [x] **`SEARCHINDEX`** `indexName` always structural: `[_m_:]<ownerNs>_<logical>` → ParseIdxFullName → **owner ns MUST be registered** (internal excepted) → `_idx_:<full>:v_*` metadata must exist (registry is SSoT, buntdb-physical-only index is rejected with precise ERR citing missing metadata). ORDER / LIMIT flags retained as today.
- [x] **`UPDATE` → strict typed-doc only (explicit user rule: UPDATE must go through ns, because it uses KeyRange and assumes typed doc semantics). NO KV-style bypass branch (unlike SEARCHKEY)**. First, `storageNsFromKRAnchor(x.LayerRoutingAnchor(kr))` MUST resolve cleanly to a single storageNs (failure → parameter ERR: "operates on typed documents only; key-range must be anchored to a registered storage namespace prefix (format: '<storageNs>:<range-suffixes>'). Use SET on the KV-path (arg1 contains ':' for full-key writes) to mutate arbitrary raw keys, or use doc-path UPDATE with a KeyRange scoped to a single registered namespace."). Resolved internal storageNs (`_doc_`, `_idx_`, `_auth_`) are short-circuited as always-valid. Any other resolved storageNs → **registry gate: ns MUST be registered** (ERR with exact resolved storageNs + anchor). Then run mutations inside a tx with KeyAttrs pk-immutable check.

#### 7.4.3 Business-Level Gates (doc-path SET-family / UPDATE / DEL)

- [x] **`SET/SETEX/SETNX` doc-path JSON validity**. Value MUST parse as a JSON object or a non-empty array of objects. Plain strings/numbers → ERR.
- [x] **SET-family KeyAttrs extraction required**. For every object, `deriveDocKey(spec, storageNs, obj)` MUST succeed. Missing top-level required `KeyAttrs` → ERR with positional `object[%d]: missing key attr: <path>` (0 rows written).
- [x] **SET-family batch atomic (all-or-nothing)**. Single `tx.Update` wraps every derived write. Any parse / KeyAttrs / duplicate-pk / NX-precondition error in the batch → 0 rows written and the command ERR with the exact reason.
- [x] **SET-family intra-batch pk collision** (two distinct objects derive the same `FullStorageKey`) → ERR at the offending array index: `duplicate key %q in single SET` (0 rows written).
- [x] **SETNX batch all-or-nothing**: before any `tx.Set`, a pre-pass runs `tx.Get` for every derived key. Any key already present → **abort with `errNxPreconditionFailed`** (reported as `0` rows for SETNX int return, not ERR).
- [x] **`DocSpec.TTL` auto-route on doc-path SET-family**. If no explicit `EX/PX` / `SETEX` ttl is 0 and `DocSpec.TTL > 0` → server side injects TTL as buntdb option. Client explicit TTLs win.
- [x] **DEL doc-path suffixes with `:` are individually rejected** by `validatePKSuffixNoColon` before any `tx.Delete` executes (Phase1 pre-check = 0 mutations).
- [x] **UPDATE KeyAttrs-PK immutable check**: for every matched row within the `tx.Update`, re-derive `oldDK` vs `newDK`. If `FullStorageKey` differs → tx aborts, 0 rows updated, ERR reports the old/new keys.
- [x] **UPDATE `LIMIT n` flag** (`n>0`, positive integer). Illegal tail tokens → parameter ERR.
- [x] **No half-written cross-layer batches**: `setBatchAtomic` and `deleteBatchAtomic` reject `len(layers)!=1` ("cannot span storage layers"). This prevents user-defined Mem flag mismatches across a doc-path batch from silently splitting writes.

#### 7.4.4 Wire Registry Commands (REGSCH/DROPSCH/REGIDX/DROPIDX)

## 11. System-Level SSoT: Global Separators & Naming Convention（系统级全局分隔符 & 命名规范 — 绝对底线）

> ⚠️ **本节是本 FR 的「宪法底线」**。本节内容是架构级的**非可选、非协商、零歧义**的约定。任何实现（M1-M7）都**不允许偏离本节的任何一条规则**。如果实现与本节冲突，必须以本节为准修改实现；反之则永远不允许出现「特殊 case」破坏此约定。一旦进入 M1 Implementation，本节内容要**byte-for-byte 迁移到 docs/architecture.md 作为全项目唯一 SSoT**，本文档只保留超链接引用。

### 11.1 底线分隔符约定（3 条 — 用户 2026-08-22 最终决策，一字不改）

| # | 约定 | 精确格式 | 常量名（实现时） | 语义说明 & 反例 |
|---|---|---|---|---|
| **1** | **Namespace（storageNs 之间）与 suffix 之间用 `:`** | `<storageNs>:<suffix>` | `contract.StorageKeySeparator = ":"`（已存在，不变） | `user:0100` → storageNs=`user`, suffix=`0100`。**这是整个 buntdb key 空间里唯一的「层级分隔符」**。任何「不同 namespace 节点间的分界」都只能用 `:`，不能用 `_` 或其它字符。**反例：storageNs 与 suffix 之间不能写 `user_0100`（会被解析成一个整体 storageNs=`user_0100` + 空 suffix，非法）**。 |
| **2** | **存在内存（`Mem()=true`）时，storageNs 前面自动前置 `_m_:`（两层 namespace）** | mem storageNs = **`_m_:<namespace>`** → 完整 mem user key = `_m_:<namespace>:<pk>` | 实现时在 `storageNamespace[D]` 里写：`if d.Mem() { return MemNsPrefix + StorageKeySeparator + d.Namespace() }` | 等价于「`_m_` 是一棵独立的 virtual root tree，下面再挂所有 user 的 namespace」。因此 mem 层 user 行永远有**两个 `:`**，即 `_m_:hot:0100`（第一层 `_m_:` 表示 in-memory 层；第二层 `hot:` 表示 user 定义的 doc namespace = `hot`；第三层 `0100` = pk-suffix）。**反例：旧格式 `_m_hot:0100`（无中间 `:`，把 `_m_hot` 当成了一个整体 storageNs）在此约定下是非法的**，必须淘汰。 |
| **3** | **Key 的属性（KeyAttrs 多段）连接时用 `_`** | pk-suffix = `seg1_seg2_..._segN` | `contract.KeyAttrsJoin = "_"`（实现时新增，不得与 StorageKeySeparator 混用） | KeyAttrs = [tenant, id] → storage key = `<storageNs>:<tenant>_<id>`。例如：`tenantuser:acme_202`（disk）/ `_m_:hot:acme_202`（mem）。** pk-suffix 内部绝对不允许出现 `:`**，所有多段拼接一律用 `_`；这样才能保证「**整个 storage key 中只有 storageNs 边界有 `:`，suffix 里永远没有 `:`**」→ scopeGuard 按冒号切一次就能正确拿到 storageNs 边界，零歧义。**反例：旧格式 `<ns>:acme:202`（KeyAttrs 多段也用 `:`）在此约定下非法**，会被 scopeGuard 误判成 storageNs=`acme` 下的 `202` 而越界。 |

### 11.2 约定的直接推论（3 条 — 从 11.1 自动导出，实现时同样强制）

> 下面 3 条都**不是独立决策**，只是把 11.1 套在 Index/Internal/Scope 三个具体场景下的必然结果。如果 11.1 不改，这 3 条也没有任何讨论空间。

#### 推论 1：IdxFullName 的生成规则（Index full name 与 storageNs 对应）

```
IdxFullName[D](logical) = storageNs + "_" + strings.ToLower(logical)
其中 storageNs = Mem() ? "_m_:<namespace>" : "<namespace>"
```

**结果形状**：`<full_index_name>` = **`[_m_:]<namespace>_<logical>`**（注意 mem 层 `_m_:` 后面跟 `<namespace>`，再跟 `_` 接 logical）。

**示例矩阵**：

| D.Namespace | D.Mem() | logical name | IdxFullName 输出 | 反例（非法） |
|---|---|---|---|---|
| `user` | false | `ByAge` | `user_byage` | `User_ByAge`（大小写不一致；未统一 lowercase）|
| `hot` | true | `Price` | `_m_:hot_price` | `_m_hot_price`（缺中间 `:`）/ `_m_:hot:price`（用 `:` 而非 `_` 接 logical）|

**同步约束**：
- `_idx_` internal 元数据键 = `_idx_:<full_index_name>`（`_idx_` 作为 internal storageNs → 再接 `:` suffix = full name）。示例：`_idx_:user_age`、`_idx_:_m_:hot_price`。
- `_doc_` internal 元数据键 = `_doc_:<storageNs>`（因为一张 Doc 在 storage 层的唯一标识就是它的 storageNs）。示例：`_doc_:user`、`_doc_:_m_:hot`。

#### 推论 2：DescribeDoc(ns) 精确查询前缀（无需全扫）

因为推论 1 已经把 `<ns>_` 编码到 `<full_index_name>`，且 Index 元数据键是 `_idx_:<full_index_name>`，所以 **DescribeDoc(ns = "user") 不需要扫 `_idx_:*` 全库**，只需要：

```
buntdb.AscendKeys(tx, "_idx_:user_*", cb)
```

就能精确拿到 user 下的所有 index meta。对应 mem 层 hot doc = ns=`hot` & Mem=true → glob = `_idx_:_m_:hot_*`。

> 这就是「命名约定天然编码归属」的数学基础：只要 11.1 的三条底线不破，上面这个 glob 就是**充要条件**（不多不少，正好是该 ns 下所有 indexes），不需要任何额外 join 或索引字段冗余。

#### 推论 3：Scope 拆分 & StorageNs 解析算法升级（统一共享 helper）

因为 11.1 强制了「**storage key 中 suffix 永远没有 `:`**」，所以 scope 的拆分永远是「**找最后一个 `:` 的位置并在它之前切出 storageNs**」？不 — 更精确地说：由于 **storageNs 本身可能包含多个 `:`（mem 层 storageNs = `_m_:hot` 就有一个 `:`）**，旧的 naive 算法「`strings.IndexByte(key, ':')` → 第一个冒号之前」在 mem 层是**错的**（会把 `_m_:hot:0100` 第一个冒号前当成 `_m_`，实际 storageNs 是 `_m_:hot`）。

所以必须把解析算法升级为「**从右往左，最后一个 `:` 之前 = storageNs；最后一个 `:` 之后 = suffix**」（因为 suffix 永远不含 `:` — 11.1 约定 3）。**这是 scopeGuard 在 mem 层新格式下唯一不会错的算法**：

```
SplitStorageKey(key string) → (storageNs string, suffix string, ok bool)
{
   i = strings.LastIndexByte(key, StorageKeySeparator[0]) // 找最后一个 ":"
   if i < 0 { return "", key, false }    // 裸 KV，无 namespace（Strict 模式下会白名单处理）
   storageNs = key[:i]
   suffix    = key[i+1:]
   return storageNs, suffix, true
}
```

> **为什么 last-colon 一定对？** 数学归纳：
> - 如果是 disk Doc user → `user:0100` → 最后一个 `:` 位置 4 → storageNs=`user`, suffix=`0100` ✅
> - 如果是 mem Doc hot → `_m_:hot:0100` → 最后一个 `:` 位置 7 → storageNs=`_m_:hot`, suffix=`0100` ✅（正确识别了两层 storageNs）
> - 如果是 internal metadata → `_doc_:user` → 最后一个 `:` 位置 5 → storageNs=`_doc_`, suffix=`user` ✅（正确识别 internal storageNs）
> - 如果是 multi-segment KeyAttrs Doc → `tenantuser:acme_202` → 最后一个 `:` 位置 10 → storageNs=`tenantuser`, suffix=`acme_202` ✅（suffix 内含 `_` 但无 `:`，last-colon 不被混淆）

在此算法基础上再导出 3 个配套 helper（所有实现必须从这 3 个 helper 读，**禁止散落硬编码 `LastIndexByte`**）：

```
// 1. 白名单判定（Strict Mode §5.3）
IsInternalStorageNs(storageNs string) bool → storageNs != "" && storageNs[0] == '_'

// 2. 把 storageNs 反解回 user Doc 的 namespace（剥掉 mem 前缀）
StripMemPrefix(storageNs string) (ns string, isMem bool) →
   if strings.HasPrefix(storageNs, contract.MemNsPrefix + contract.StorageKeySeparator) = "_m_:"
        return strings.TrimPrefix(storageNs, "_m_:"), true
   else return storageNs, false

// 3. KeyAttrs 一致性校验：从 suffix 拆出各段 KeyAttrs value（用 _ 切）
SplitKeyAttrsSuffix(suffix string, segCount int) ([]string, error) →
   if segCount <= 1 { return [suffix], nil }   // 单段直接返回
   segs = strings.SplitN(suffix, contract.KeyAttrsJoin, segCount)
   if len(segs) != segCount → ERR "KeyAttrs segment count mismatch"
   return segs, nil
```

### 11.4 实现时的「零硬编码」门禁

为了保证 11.1 + 11.2 的一致性，实现时必须通过以下 2 条门禁（M1 DoD 中作为编译/静态检查项）：

1. **No scattered split**：全局 `grep -rn "strings.Index\|strings.LastIndex\|strings.Split\|strings.Contains" --include="*.go" client server x internal` → 凡是与 storage key 解析/拼接相关的字符串操作，**只允许调用 `internal/shared.go` 中 11.2 定义的 5 个共享 helper**（`SplitStorageKey`、`IsInternalStorageNs`、`StripMemPrefix`、`SplitKeyAttrsSuffix`、以及已有 `ScopeKeyRange` + `ValidateKeyPattern` + `ValidateIdxName`）。任何散落的 `:` 或 `_` 相关硬编码都必须被**替换为 helper 调用**或给出非 storage-key 解析的正当理由。
2. **Constant single source of truth**：全局 `grep -rn '":"\|"_"' --include="*.go"`（literal `":"` 和 `"_"`）→ 除了 test 断言的 raw string literal 与 JSON 路径外，**生产代码中拼接 storage key / index name 必须使用 `contract.StorageKeySeparator` 与 `contract.KeyAttrsJoin` 常量**，不允许写字面量 `:` 或 `_`。

两条门禁过不了 → milestone 不得合并。
